# Этап 6: Memory

## Что готово

`core/memory.py` хранит и восстанавливает контекст через репозитории Supabase:

- тему обращения;
- установленные обстоятельства (до 20 коротких строк);
- имя клиента, если оно известно;
- этап записи: idle, topic, name, phone, consent;
- сообщения клиента и ассистента в правильном порядке;
- версию уведомления о хранении истории и время явно полученного согласия.

`ConversationState` и `MemorySnapshot` неизменяемы. Их repr не содержит имени,
обстоятельств и текста переписки. Memory не хранит общий словарь сессий или
локальный кэш: каждый снимок читается из БД с UUID и секретом владельца.
Новый объект Memory восстанавливает контекст при наличии тех же реквизитов.
Восстановление после перезапуска сервера также требует сохранённых реквизитов
клиента; их безопасная привязка к браузеру появится на этапе Gradio.

Структурированные сведения передаёт проверенный серверный код. Memory сама
не извлекает имена и обстоятельства из свободного текста, не вызывает LLM и
не считает высказывания модели доказанными фактами. Автоматическое заполнение
состояния будет частью последующего Assistant.

## Работа с Memory в Python

Пример только для синтетических данных в отдельном тестовом проекте. Вызовы
действительно записывают данные в настроенный Supabase. `test-only-notice-v1` —
обозначение теста, не утверждённый текст согласия для реальных клиентов.

```python
from dataclasses import replace
from uuid import uuid4

from config import load_supabase_settings
from core.memory import Memory
from core.router import BookingStage
from database.repositories import Repositories
from database.supabase_client import SupabaseClient

with SupabaseClient(load_supabase_settings()) as client:
    repositories = Repositories(client)
    memory = Memory(repositories)
    credentials = repositories.new_credentials()  # UUID и случайный секрет
    snapshot = memory.initialize(
        credentials, history_consent=True, notice_version='test-only-notice-v1'
    )
    message_id = str(uuid4())  # сохранить для возможного повтора после тайм-аута
    snapshot = memory.append(
        credentials, message_id=message_id, role='user',
        content='Тестовый вопрос об алиментах', expected_version=snapshot.version
    )
    state = replace(
        snapshot.state, legal_topic='Взыскание алиментов',
        facts=('Тестовое обстоятельство',), client_name='Тестовое имя',
        booking_stage=BookingStage.NAME
    )
    snapshot = memory.save_state(
        credentials, expected_version=snapshot.version, state=state
    )
    # Новый объект читает состояние из БД, а не из старого объекта Memory:
    restored = Memory(repositories).load(credentials)
    assert restored.state == state
    result, snapshot = memory.route(credentials, 'Тестовое имя')
    print(result.intent.value)  # BOOKING, с учётом сохранённого этапа
    memory.clear_history(credentials)
    memory.delete_session(credentials)  # удаление только тестовой сессии
```

`history_consent=True` устанавливается сервером **после явного действия пользователя**
под показанным уведомлением. Не передавайте сюда результат свободного вывода модели.
Согласие на историю отдельно от согласия на заявку; Memory не предоставляет
агенту разрешение создать заявку. Текст и юридическая корректность уведомления
требуют подготовки до публичного запуска, как и оценка инфраструктуры обработки данных.

## Согласованность, ошибки и очистка

Миграция добавляет три закрытых серверных RPC: `memory_snapshot`, `memory_append`,
`memory_health`. Снимок состояния и последних N сообщений получается под одной
блокировкой сессии в одной транзакции. Стандартный лимит истории — 40, максимум 100.
Структурированные обстоятельства сохраняются отдельно и остаются доступными,
когда старые сообщения выходят за пределы выбранного окна.

При добавлении нового сообщения проверяются сохранённое согласие и ожидаемая
версия сессии. Если два запроса пришли с одной версией, один новый запрос получит
конфликт: вызывающая сторона должна загрузить свежий снимок и заново оценить действие.
Повтор того же UUID сообщения с теми же данными не создаёт дубля и допускается
после повышения версии. Изменённый текст с прежним UUID отклоняется.

`save_state` применяет сравнение версии и не позволяет менять поля согласия.
Автоматического повтора записи после ошибки или конфликта нет. Не показывайте
пользователю успешное сохранение при тайм-ауте или недоступности БД.
Ошибочный/чужой снимок, неизвестные поля состояния и сообщения с ролью system
отклоняются вместо молчаливой потери или подмены контекста.

Очистка удаляет сообщения и сбрасывает **всё** состояние, включая имя, обстоятельства,
этап записи и согласие на историю. Для новых сообщений потребуется повторное согласие.
Старая запись, которая ожидала прежнюю версию до очистки, не восстановит историю.
Сама очистка сохраняет заявки — для них есть отдельное удаление на уровне репозитория.
Полное удаление сессии удаляет также заявки и их журналы каскадно.

Снимок — состояние на момент чтения; дальнейшая транзакция может его изменить.
Memory обеспечивает атомарность **отдельных** операций, а не целого цикла ответа LLM.
Очередь и контроль версии полного цикла будут подключены в Assistant/Gradio.
Методы старого низкоуровневого репозитория остаются административными операциями:
веб-запросы должны проходить через Memory, а не через произвольный прокси RPC.

История и состояние содержат персональные данные. `snapshot.messages` и
`snapshot.state` нельзя напрямую передавать зарубежной LLM. Санитизация и
сборка контекста для модели будут реализованы в Assistant; на этом этапе Memory
в облачную модель ничего не отправляет.

Если в тестовой БД осталось произвольное состояние из прежних ручных экспериментов,
неизвестный формат будет отклонён. Используйте новые тестовые сессии или явно
очистите свою старую сессию её реквизитами. Автоматически старые данные не стираются.

## Проверки

Проверено на Python 3.10.1: **71 Python-тест прошёл**, включая 18 новых тестов Memory.
На временном PostgreSQL 17.6 успешно применена базовая схема и дважды миграция 002.
Через тестовый HTTP-мост проверены восстановление контекста новым клиентом,
изоляция двух пользователей, сохранённые тема/обстоятельства/имя/этап, ограничение
окна истории, повтор сообщения, конфликт двух одновременных записей и очистка
без восстановления старым запросом, включая повтор после нового согласия.
Проверены также отказ чужому секрету и недоступность удалённой сессии.
Сервер остановлен, временный кластер удалён. Облачный Supabase не проверен.
Команда `--check-memory` без настроек ожидаемо завершилась с кодом 1 до сети.

```powershell
.\.venv\Scripts\python.exe -m pytest .\tests\test_memory.py -q
.\.venv\Scripts\python.exe -m pytest -q
# PostgreSQL должен быть установлен и доступен в PATH:
.\.venv\Scripts\python.exe -u .\tests\check_schema_local.py
```

Последняя команда проверяет исходную схему, повторное применение миграции и Memory
на настоящей временной PostgreSQL-базе. Тестовый HTTP-мост переводит вызовы
репозиториев в SQL; облачный PostgREST этим не проверяется.
Временный сервер работает на 127.0.0.1 с паролем, затем останавливается и удаляется.
