# Этап 8: Telegram и очередь уведомлений

## Реализовано

- `tools/telegram_tools.py`: настоящий HTTPS Telegram Bot API и функция
  `send_telegram_notification(lead, *, client)`.
- `tools/notification_worker.py`: обработчик постоянной очереди в Supabase.
- `tools/telegram_setup.py`: получение ID чатов своего бота без вывода текстов сообщений.
- `database/migrations/004_telegram.sql`: аренда задач, подтверждение результата,
  идентификатор сообщения Telegram, общая пауза при ограничении частоты.
- Отдельные команды проверки, технической отправки и обработки очереди.

Заявка и задача уведомления по-прежнему создаются атомарно инструментом этапа 7.
Отправщик не зависит от модели и не доступен через её tool dispatcher. Получатель
берётся только из серверной конфигурации, а не из аргументов клиента/модели.

## Что требуется от владельца

1. В своём Telegram создайте бота через [BotFather](https://t.me/BotFather), командой
   `/newbot`, и сохраните выданный токен локально в `.env`.
   [Официальная инструкция](https://core.telegram.org/bots/features#creating-a-new-bot).
2. Откройте личный чат с созданным ботом и нажмите Start или отправьте `/start`.
   Приложение использует его для исходящих уведомлений; обработчик ответов на
   входящие команды здесь не запускается.
3. Получите ID этого чата командой ниже. Она вызывает `getUpdates` без `offset`,
   не подтверждает получение обновлений и не меняет webhook. Выводит только ID/тип,
   без имён, текста сообщений и токена. Если у бота уже есть webhook или другой
   потребитель обновлений, не меняйте их автоматически: используйте выделенного бота
   либо получите ID из своей действующей интеграции.

```powershell
Set-Location 'C:\Users\user\Desktop\дима разработка\03-AI Assistant urist\legal_ai_consultant'
if (-not (Test-Path -LiteralPath '.\.env')) {
    Copy-Item -LiteralPath '.\.env.example' -Destination '.\.env'
}
notepad .\.env
# Сначала заполните только TELEGRAM_BOT_TOKEN и напишите своему боту /start:
.\.venv\Scripts\python.exe -m tools.telegram_setup
```

4. Запишите полученный числовой ID в `TELEGRAM_CHAT_ID`. Токен и ID не отправляйте
   в чат и не включайте в исходники/GitHub. Токен не нужно вставлять в URL браузера.

```dotenv
TELEGRAM_BOT_TOKEN=YOUR_BOT_TOKEN
TELEGRAM_CHAT_ID=YOUR_NUMERIC_CHAT_ID
TELEGRAM_TIMEOUT_SECONDS=10
TELEGRAM_INCLUDE_CONTACT=false
NOTIFICATION_MAX_ATTEMPTS=5
NOTIFICATION_LEASE_SECONDS=120
```

5. В SQL Editor тестового Supabase выполните **полный**
   `database/migrations/004_telegram.sql` после базовой схемы и миграций 002, 003.
   Миграция 004 допускает повторное применение. Базовую схему повторно не запускайте.
6. Проверьте настройки. Следующие команды ничего не отправляют:

```powershell
.\.venv\Scripts\python.exe .\app.py --check-notifications
.\.venv\Scripts\python.exe .\app.py --check-telegram
```

Первая проверяет RPC/права БД; вторая — токен через `getMe` и адресата через `getChat`.
Ни одна не доказывает фактическую доставку сообщения.

7. Для одного реального технического сообщения без данных клиентов:

```powershell
.\.venv\Scripts\python.exe .\app.py --test-telegram
```

Успех выводится только после ответа Telegram с `message_id` и ожидаемым ID чата.
Это подтверждение принятия Telegram, не прочтения юристом. Проверьте сообщение в
своём Telegram. Настройки Supabase для этой технической отправки не требуются.

## Запуск обработчика

Для существующих **тестовых** заявок в настроенном Supabase:

```powershell
# Один пакет до 10 задач; действительно отправляет сообщения:
.\.venv\Scripts\python.exe .\app.py --send-notifications

# Постоянная обработка в отдельном PowerShell, остановка Ctrl+C:
.\.venv\Scripts\python.exe .\app.py --notification-worker
```

Постоянный обработчик проверяет очередь каждые 2 секунды. Это отдельный серверный
процесс; запуск будущего Gradio не заменяет его. Развёртывание обработчика будет
подготовлено с конфигурацией Render на этапе 12. Если процесс остановлен, новые
задачи остаются в Supabase. На старте проверяются схемы и права всех предыдущих этапов.

Статусы консоли: `sent`, `retry_scheduled`, `needs_attention`, `unconfirmed`,
`cancelled_or_expired`. Отсутствие задач не считается ошибкой. Не печатаются контакты,
текст дела, ключи и идентификаторы аренды. При недоступности БД процесс завершается
с безопасной ошибкой; невыполненные задачи остаются в БД.

## Содержание уведомления и минимизация

Сообщение содержит ID заявки, первое слово имени, маскированный телефон,
обобщённую юридическую тему и дату регистрации в UTC+03:00. Свободный текст темы
заменяется известными метками; описание дела, история, фамилия из отдельного слова
и секрет сессии не отправляются. Нестандартное имя заменяется словом «Клиент».

Для обратной связи полный контакт доступен юристу в серверной базе. Если после
оценки обработки данных полный телефон нужен именно в Telegram, владелец может
установить `TELEGRAM_INCLUDE_CONTACT=true`. По умолчанию это отключено.
Это не делает передачу автоматически соответствующей требованиям законодательства.
Реальные данные не используйте до проверки инфраструктуры и утверждения документов.

Отправляется простой текст без `parse_mode`, без предпросмотра ссылок и с
`protect_content=true`. Токен находится в пути Bot API согласно протоколу;
его маскирует фильтр обычных логов httpx. Не включайте внешние отладочные трассировки
HTTP/сетевого трафика с секретами и не публикуйте содержимое `.env`.

## Надёжность

Одна задача атомарно берётся в аренду через `FOR UPDATE SKIP LOCKED`. Случайный
`claim_token` защищает запись результата от устаревшего обработчика. Аренда по
умолчанию 120 секунд; лимит попыток — 5. За раз берётся одна задача, чтобы остальные
не ожидали отправки с уже истекающей арендой.

При явном отказе `ok=false` с 429/5xx или невозможности установить соединение
планируется повтор с задержкой. Базовая задержка — 60 секунд, затем удваивается
до 3600 секунд; `retry_after` Telegram учитывается, если он больше этой задержки.
HTTP-операция сама по себе не повторяется автоматически внутри клиента.

Для `429` устанавливается также общая пауза `telegram_delivery_state` для одного
настроенного бота/чата. Она переживает перезапуск и блокирует новые задачи до
разрешённого срока, в том числе если текущая задача исчерпала попытки.
Уже выполняющиеся запросы от других процессов отменить этим нельзя.

При тайм-ауте после начала отправки, некорректном ответе, истечении аренды или
ошибке БД после принятия сообщения результат может быть неизвестен.
Автоматическая повторная отправка в таком случае **не выполняется**. Задача
остаётся со статусом `failed`, `next_attempt_at=NULL` и безопасным кодом причины;
после сбоя записи результата она сначала остаётся `sending`, затем переводится
в это состояние при следующем запуске очереди.

Это уменьшает риск дублей, но не гарантирует «ровно одну доставку» при сетевом сбое.
Перед ручным повтором остановите старые обработчики, проверьте чат по ID заявки
и осознанно решите, допустим ли риск дубля. Само приложение такие задачи не сбрасывает.
Для просмотра задач без контактов в SQL Editor:

```sql
select id,lead_id,status,attempts,error_message,next_attempt_at
from public.notification_logs
where status='failed' and next_attempt_at is null;
```

Заявка не удаляется при ошибке Telegram. Удаление заявки удаляет её задачу очереди.
Обработчик проверяет наличие задачи непосредственно перед HTTP-вызовом, но удаление
в момент уже начавшейся отправки не отменяет внешнее сообщение. Уже доставленные
сообщения не удаляются каскадным удалением строк БД.

## Проверки и фактическое состояние

```powershell
.\.venv\Scripts\python.exe -m pytest .\tests\test_telegram.py -q
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -u .\tests\check_schema_local.py
```

Проверено на Python 3.10.1: **109 Python-тестов прошли**. На временном PostgreSQL
17.6 проверены повторное применение миграции 004, закрытые права, эксклюзивный
захват одной задачи шестью обработчиками, путь Tool → outbox → worker → Telegram
через тестовый ответчик → `sent`, повтор после `429`, общая пауза и восстановление
новым клиентом, лимит попыток, устаревший токен, неизвестный результат, удаление
задачи и ошибка БД после отправки. Временный сервер остановлен и удалён.

Облачные Supabase и Telegram **не проверены**: URL/ключ Supabase, токен бота и ID
чата пока не предоставлены. Сетевые ответы Telegram в тестах подменены, реальных
сообщений тесты не отправляли. Нужна техническая проверка владельца по шагам выше.
