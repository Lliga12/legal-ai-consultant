# Этап 9: Judge — проверка ответа до отправки

## Что готово

`core/judge.py` принимает черновик и серверный `JudgeContext`, возвращает
`JudgeResult`. Для клиента используется **только `result.answer`**. Если проверки
не пройдены, исходный текст заменяется известным уточнением или правилом стоимости
из базы знаний. Исходный плохой черновик не возвращается в полях результата.

`core/prompts.py` содержит загрузчик базы знаний, общие инструкции будущего
Assistant и отдельные инструкции проверяющей модели. Judge читает настоящий
`knowledge/knowledge.txt`. Генерация консультаций и включение проверки перед
отправкой в Gradio будут собраны на этапе 10; веб-чата на этом этапе ещё нет.

## Локальные проверки

- Пустой и слишком длинный ответ.
- Типовые выдуманные цены, бесплатность и скидки. Точные строки раздела стоимости
  базы знаний допускаются. Сейчас числового прайса в ней нет.
- Гарантии результата и категоричные обещания победы.
- Номера статей, кодексы, ссылки и типовые точные правовые сроки. Механизма проверки
  актуальности норм нет, поэтому такие утверждения отклоняются. Judge не ищет законы.
- Типовые придуманные сведения о практике и обстоятельствах клиента.
- Регистрация, отправка Telegram и удаление без подтверждения сервера.
- Типовые телефоны, email, паспортные/страховые/банковские номера, UUID и ключи.
  Дополнительно сервер передаёт известные ему имена, контакты и секреты.
- Запрос контактов без серверного разрешения или после отказа от согласия.
- Типовые команды изменения инструкций, активный HTML и некоторые Unicode-обходы.
- Простая связь ответа с вопросом по словам и намерению.

Это консервативные правила, не полный анализ языка. Сложные перефразировки,
неизвестные имена/адреса и неверные правовые обобщения без ссылок и чисел могут
не распознаться. Возможны лишние отклонения правильных ответов. Разрешение по
правилам не доказывает релевантность, отсутствие любых выдумок или юридическую точность.

## Подтверждения действий

`ActionEvidence` создаёт только сервер из результатов **текущего обращения**:
`lead` — настоящий `LeadResult`, `notification_sent` — подтверждённая отправка,
`history_deleted_count` / `leads_deleted_count` — результаты удаления,
`session_deleted` — подтверждение удаления сессии. Не создавайте его из JSON
клиента/модели и не используйте результаты других сессий.

Действия допускаются в коротких канонических формулировках. Иной пересказ Judge
может заменить, самостоятельно добавив подтверждённый серверный статус. Произвольный
текст `lead.message` для этого не используется. `pending`, `failed`, `sending`
уведомления не подтверждают отправку. Заявка не означает назначения консультации.
После `unconfirmed` допустимо «Регистрация заявки не подтверждена», но не
«Заявка не создана»: после тайм-аута БД результат может быть неизвестен.

## Необязательная проверка смысла через модель

По умолчанию `JUDGE_MODE=local`, запросов к модели нет. В режиме `llm` после
локальных проверок возможен **один** вызов существующего адаптера. Модель возвращает
строгий JSON с `approved` и известными кодами `issues`. Лишние/повторяющиеся поля,
Markdown вместо JSON, неизвестные коды, несогласованные значения или ошибка API
приводят к замене черновика. Модель не переписывает ответ, не вызывает инструменты
и не может отменить локальный запрет.

Нужны одновременно `JUDGE_MODE=llm`, настроенный адаптер в `Judge(..., llm=shared_adapter)`
и серверный `cloud_review_allowed=True`. Последний флаг — внутреннее разрешение,
не юридическое заключение и не замена согласия. Клиент/модель не выставляют его.
По умолчанию он false. До запроса известные частные значения, типовые контакты,
UUID и ключи заменяются на `[СКРЫТО]`. Это **не универсальное обезличивание**:
свободное описание дела может сохранять идентифицирующие сведения. Не разрешайте
облачную проверку реальных данных без оценки состава передачи и инфраструктуры.
Исходную переписку/Memory напрямую в модель Judge не передавайте.

Запрос использует тайм-ауты и бюджет адаптера этапа 3. Общий адаптер нужно
переиспользовать: генерация ответа и Judge расходуют общий счётчик. Повторов и
бесконечной перегенерации нет. Модель тоже может ошибиться и не проверяет закон.

## Настройки и проверка в PowerShell

Новых ключей, SQL-миграций и действий в Supabase на этом этапе **не требуется**.
В `.env.example` добавлены необязательные настройки:

```dotenv
JUDGE_MODE=local
JUDGE_MAX_ANSWER_CHARS=4000
```

Предел черновика — 512–8000 символов, по умолчанию 4000. Вопрос — до 4000 символов.
Если политика стоимости базы меняется, правила и тесты Judge также пересматриваются.

```powershell
Set-Location 'C:\Users\user\Desktop\дима разработка\03-AI Assistant urist\legal_ai_consultant'
.\.venv\Scripts\python.exe .\app.py --check-judge
.\.venv\Scripts\python.exe -m pytest .\tests\test_judge.py -q
.\.venv\Scripts\python.exe -m pytest -q
```

`--check-judge` всегда локальный, даже при `JUDGE_MODE=llm` в `.env`. Он показывает
замену выдуманной цены, гарантии и неподтверждённой регистрации, а также прохождение
обычного уточняющего ответа. LLM, Supabase и Telegram не вызываются; плохой текст
не печатается. Настройка внешних сервисов для этой проверки не нужна.

## Использование сервером

```python
from config import load_judge_settings
from core.judge import ActionEvidence, Judge, JudgeContext
from core.router import Intent

judge = Judge(load_judge_settings())
context = JudgeContext(
    question='Сколько стоит консультация?', intent=Intent.PRICE,
    actions=ActionEvidence(),  # действий ещё не было
)
result = judge.review('Консультация стоит 5000 рублей.', context)
print(result.answer)  # индивидуальная стоимость из knowledge.txt
assert result.replaced
```

Для дела сервер передаёт `facts` (кортеж установленных обстоятельств), `private_values`
(имена/контакты текущей сессии), `secrets` и подтверждения действий. Это серверные
поля, не произвольный вывод модели. `contact_collection_allowed` выставляется после
информирования и проверки условий сбора данных. При отказе — `consent_refused=True`.
Затем сохраняется и отправляется только `result.answer`, а не исходный draft.

`result.approved` означает прохождение исходным черновиком выбранных проверок;
`replaced` — замену, `issues` — безопасные коды причин. `semantic_checked=True`
означает полученный и проверенный по формату вердикт модели. Даже `approved=True`
не является юридической экспертизой. Контекст и текст результата скрыты в repr.
