# Этап 7: Tool Calling — создание заявки

## Что реализовано

`tools/lead_tools.py` содержит серверный `LeadTools.create_lead`:

```python
create_lead(name, phone, legal_topic, description, session_id, consent, *, request_id)
```

Шесть основных аргументов соответствуют заданию. Дополнительный `request_id`
обязателен: его сервер берёт из сохранённого черновика, а не из свободного вывода
модели. Сам экземпляр инструмента привязан к `SessionCredentials` и версии согласия.
UUID сессии без её секрета не разрешает доступ.

Инструмент нормализует российский телефон, проверяет имя, тему, описание, согласие
и принадлежность сессии. Заявка сохраняется через настоящий RPC Supabase;
успешный результат содержит ID, дату регистрации и фактический статус задачи
уведомления. Тексты ошибок и результат не раскрывают контакты или секреты.

`dispatch` разрешает только `create_lead` и ровно шесть ожидаемых аргументов.
Модель не получает инструменты фиксации согласия, подготовки произвольных сессий,
удаления данных или выполнения SQL. Подключение этого диспетчера к полному циклу
LLM будет реализовано с Assistant; на этом этапе проверен сам серверный инструмент.

## Почему добавлен черновик

Миграция `database/migrations/003_lead_tools.sql` добавляет закрытую таблицу
`lead_requests`: один актуальный черновик на сессию. Он содержит проверенные данные,
постоянный UUID операции, версию и дату согласия, ID созданной заявки.

Сценарий сервера:

1. После информирования и согласия на хранение истории собрать минимальные данные.
2. `prepare(...)` сохраняет нормализованный черновик без согласия на регистрацию.
3. Показать клиенту сведения заявки и утверждённый текст согласия.
4. Только обработчик явного выбора клиента вызывает `record_consent(...)`.
5. `create_lead(...)` проверяет, что данные совпадают с подтверждённым черновиком.

Одного `consent=True` от модели недостаточно: SQL дополнительно проверяет сохранённое
согласие. Изменение данных или версии согласия создаёт новый UUID и сбрасывает
подтверждение. Повтор подготовки с теми же данными возвращает тот же черновик.
Отказ/отзыв через `record_consent(..., consent=False)` запрещает дальнейшую регистрацию.
Устаревшее событие согласия отклоняется по версии сессии.

Согласие на историю не заменяет согласие на заявку. Перед публичной работой нужны
реквизиты оператора, утверждённые уведомления и правовая оценка обработки данных.
Тестовые обозначения версий в примерах не являются реальными текстами согласия.

## Надёжность и уведомления

Черновик и ключ операции находятся в БД, поэтому новый объект инструмента может
продолжить работу после перезапуска при наличии реквизитов сессии и `request_id`.
Потерянный `request_id` можно восстановить повторным `prepare` с теми же данными;
это не создаёт второй черновик или заявку.

В одной транзакции создаются заявка и `pending`-запись в `notification_logs`.
Идентификатор черновика используется как ключ идемпотентности. Повторные и
одновременные вызовы возвращают один ID заявки. Если вставка задачи уведомления
не удалась, заявка и отметка `lead_id` черновика тоже откатываются.

Telegram пока **не отправляется**: на этапе 7 создана постоянная задача доставки.
Функция `send_telegram_notification` и обработчик очереди появятся на этапе 8.
Ошибка будущей доставки не отменяет успешно сохранённую заявку.

Результаты `LeadResult`:

| status | Значение |
| --- | --- |
| `created` | БД подтвердила новую заявку и её ID |
| `already_exists` | Та же заявка уже зарегистрирована |
| `validation_error` | Ошибка входных данных или неизвестный инструмент |
| `consent_required` | Нет явного/сохранённого согласия |
| `conflict` | Данные или версия операции изменились |
| `session_unavailable` | Сессия/черновик недоступны |
| `unconfirmed` | Сохранение не подтверждено, в том числе после тайм-аута |

`success=True` только для первых двух статусов. При `unconfirmed` нельзя утверждать,
что заявки нет: транзакция могла завершиться до разрыва связи. Повторять нужно с тем
же черновиком и теми же данными. Автоматического повтора HTTP нет.

Очистка истории теперь удаляет также черновик и его согласие, сохраняя готовые
заявки. Удаление заявок удаляет черновик, чтобы запоздалый повтор не создал их снова.
Удаление сессии каскадно удаляет все её строки. Очистка, согласие и регистрация
сериализуются по блокировке одной сессии. Уже сохранённая до очистки заявка остаётся
до отдельного удаления. Срок хранения незавершённых черновиков нужно определить
до публичного запуска; автоматический срок в этом этапе не придуман.

Низкоуровневые RPC этапа 5 остаются административной инфраструктурой. Серверный
ключ позволяет обойти инструмент, поэтому его нельзя публиковать или выдавать
универсальный RPC-прокси браузеру/модели. Пользовательское оформление должно
проходить через LeadTools и сохранённое подтверждение.

## Что требуется от владельца

В SQL Editor тестового Supabase выполните миграции в порядке:

1. `database/schema.sql` — один раз, если базовая схема ещё не установлена.
2. `database/migrations/002_memory.sql` — если ещё не применена.
3. **`database/migrations/003_lead_tools.sql`** — новая миграция этапа 7.

Базовую схему повторно выполнять не нужно. Миграции 002 и 003 допускают повторное
применение. Действующий SQL-скрипт — источник истины; код в документах этапов является
снимком для просмотра. Перед работой с существующими таблицами соблюдайте ограничения
выделенного проекта из этапа 5.

```powershell
Set-Location 'C:\Users\user\Desktop\дима разработка\03-AI Assistant urist\legal_ai_consultant'
.\.venv\Scripts\python.exe .\app.py --check-tools
```

Команда проверяет базовую схему, Memory и закрытые RPC/таблицу черновиков.
Она не создаёт заявок и не отправляет уведомления. Настройки `SUPABASE_URL` и
серверного `SUPABASE_KEY` берутся из `.env`; ключ LLM и Telegram не требуются.
Без настроек команда завершается до сети. Реальные облачные интеграции пока
не подтверждены: настройки владельца не предоставлены.

## Пример серверного вызова

Пример предназначен только для синтетических данных в тестовом Supabase.
Реальный интерфейс согласия будет подключён на этапе Gradio.

```python
from config import load_supabase_settings
from core.memory import Memory
from database.repositories import Repositories
from database.supabase_client import SupabaseClient
from tools.lead_tools import LeadTools

with SupabaseClient(load_supabase_settings()) as client:
    repo = Repositories(client)
    credentials = repo.new_credentials()
    memory = Memory(repo)
    snapshot = memory.initialize(
        credentials, history_consent=True, notice_version='synthetic-history-notice'
    )
    tools = LeadTools(repo, credentials, consent_version='synthetic-lead-consent')
    data = dict(name='Тест', phone='8 (000) 000-00-00',
                legal_topic='Тестовая тема', description='Синтетическое описание')
    request = tools.prepare(**data, expected_version=snapshot.version)
    # В рабочем приложении: только после явного выбора клиента, вне вызовов модели.
    request = tools.record_consent(
        request.request_id, consent=True, expected_version=request.session_version
    )
    result = tools.create_lead(
        **data, session_id=credentials.session_id, consent=True,
        request_id=request.request_id
    )
    print(result.status.value, result.lead_id)  # без контактов и секретов
    memory.delete_session(credentials)  # удалить только созданные тестовые данные
```

## Проверки

Проверено на Python 3.10.1: **88 Python-тестов прошли**, включая 17 новых тестов
инструмента. На PostgreSQL 17.6 успешно проверены повторное применение миграции,
привязка согласия к данным, отказ и отзыв согласия, чужая сессия, смена черновика,
шесть одновременных вызовов с одним результатом, восстановление новым клиентом,
сохранение заявки при ошибке доставки и откат при ошибке записи outbox.
Повторный вызов сохраняет исходную дату согласия уже зарегистрированной заявки.
Также проверены варианты PostgreSQL-дат с 1–6 знаками дробных секунд для Python 3.10.
`--check-tools` без настроек завершился до обращения к сети. Облачный Supabase и
Telegram этими проверками не подтверждены.

```powershell
.\.venv\Scripts\python.exe -m pytest .\tests\test_tools.py -q
.\.venv\Scripts\python.exe -m pytest -q
```
