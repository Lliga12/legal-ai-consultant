# Этап 5: Supabase

## Что готово

- `database/schema.sql`: четыре таблицы, индексы, ограничения и серверные RPC.
- `database/supabase_client.py`: HTTPS-клиент на httpx, тайм-ауты, безопасные ошибки.
- `database/repositories.py`: операции сессий, сообщений, состояния и заявок.
- `config.py`: отдельная загрузка Supabase; ключ LLM для работы с БД не требуется.
- `app.py --check-db`: проверка подключения и ограничений схемы без записи данных.
- `tests/test_database.py`: локальные проверки HTTP-контракта и валидации.
- `tests/check_schema_local.py`, `tests/schema_checks.sql`: проверка настоящим PostgreSQL.

Это инфраструктура хранения. Memory, серверная фиксация согласия в интерфейсе,
агентский инструмент создания заявки и доставка Telegram будут собраны позднее.
Облачный Supabase пока не проверен: адрес проекта и ключ не предоставлены.

## Что требуется от владельца для облачной проверки

1. Подготовьте отдельный тестовый проект Supabase. Схема предназначена для нового
   проекта без одноимённых таблиц. Не применяйте её к существующей рабочей базе.
2. В SQL Editor этого проекта вставьте **полный** `database/schema.sql` и выполните.
   Скрипт выполняется от административной роли `postgres`, одной транзакцией.
   При ошибке не запускайте отдельные части; сохраните текст ошибки без ключей и данных.
   Повторный запуск уже применённой схемы намеренно завершится ошибкой, не стирая таблицы.
3. В настройках проекта найдите Project URL и серверный Secret key (`sb_secret_...`).
   Поддерживается также legacy `service_role` JWT; `anon` и publishable не подходят.
4. Внесите значения в `.env` на своём компьютере. Ключ не отправляйте в чат,
   не сохраняйте в GitHub и не вставляйте в клиентский код.
5. Выполните `--check-db`. Успех подтверждает ответ RPC и проверенные этой RPC
   ограничения, но не заменяет проверку всего облачного сценария записи/удаления.

```powershell
Set-Location 'C:\Users\user\Desktop\дима разработка\03-AI Assistant urist\legal_ai_consultant'
if (-not (Test-Path -LiteralPath '.\.env')) {
    Copy-Item -LiteralPath '.\.env.example' -Destination '.\.env'
}
notepad .\.env
```

Заполните локально:

```dotenv
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_KEY=YOUR_SERVER_SECRET_KEY
SUPABASE_TIMEOUT_SECONDS=15
```

Значения выше — обозначения, не рабочие учётные данные.

```powershell
.\.venv\Scripts\python.exe .\app.py --check-db
```

Ожидаемый вывод после применения схемы и настройки настоящего доступа:

```text
Supabase ответил. Схема v1: RLS включён, доступ anon/authenticated закрыт.
Проверка не создавала сессий, сообщений и заявок.
```

Если отсутствует URL/ключ, запрос не отправляется. HTTP 401/403 обычно требует
проверить ключ и права; HTTP 404 — адрес проекта, применение схемы и доступность RPC
в Data API. Не считайте тайм-аут записи доказательством её отсутствия: сервер мог
выполнить транзакцию до разрыва соединения.

## Модель доступа

RLS включён для каждой таблицы. Разрешающих политик для `anon` и `authenticated`
нет; права этих ролей и PUBLIC на таблицы, последовательность и RPC отозваны.
Серверная роль получает необходимые табличные права. RPC используют
`SECURITY INVOKER`, пустой `search_path` и явно квалифицированные имена таблиц.

Серверный Secret key обходит RLS. Поэтому **каждая пользовательская операция**
репозитория передаёт UUID сессии и SHA-256 её случайного секрета. RPC проверяет
пару и блокирует строку сессии на время транзакции. В БД хранится только хеш,
в результатах операций сессии он не возвращается. Секрет — 32 случайных байта;
его утрата требует новой сессии, без восстановления по одному UUID.

Права серверного ключа позволяют обойти репозитории и обратиться к таблицам напрямую:
утечка ключа раскрывает данные. Репозитории — внутренняя серверная граница,
их нельзя выдавать клиенту как универсальный RPC-прокси. Веб-привязка секрета к
браузеру и авторизация запросов будут реализованы с Memory/Gradio.

`health` проверяет версию схемы, RLS четырёх таблиц и отсутствие прав чтения/записи
у браузерных ролей, а также EXECUTE для функций с префиксом `legal_ai_`.
Это проверка конкретных объектов, а не аудит всего проекта Supabase.
Префикс `legal_ai_` зарезервирован для этого приложения в выделенном проекте.

## Целостность и повторы

- Сообщения имеют UUID для идемпотентности и монотонный `sequence` для порядка.
  История возвращает последние N записей в хронологическом порядке, максимум 100.
- Состояние сессии — JSON-объект до 8000 байт. Обновление проверяет `version`;
  устаревшая версия отклоняется. Добавление сообщения тоже повышает версию.
- Низкоуровневая запись заявки требует `consent is True`, версии текста согласия,
  имени, нормализованного российского телефона `+7` + 10 цифр, темы и описания.
  Это контроль наличия данных, а не доказательство юридической корректности согласия.
- Сохранение заявки и `pending`-записи уведомления происходит в одной транзакции.
  Задача Telegram пока только сохраняется: отправщик появится на этапе 8.
- Одинаковый UUID идемпотентности в пределах сессии с одинаковыми данными возвращает
  прежний ID. Изменённые данные с тем же ключом вызывают конфликт.
  Другой ключ создаёт отдельную заявку: выбор и сохранение ключа реализует будущий tool.
- Автоматических повторов HTTP нет. При ручном повторе после тайм-аута сохраняйте
  исходные UUID сессии, сообщения или ключ заявки и исходные данные.

`new_credentials()` только генерирует реквизиты; `create_session(credentials)`
сохраняет их. Такое разделение позволяет повторить создание после тайм-аута,
не создавая новую сессию и не теряя секрет.

## Удаление

`clear_history` удаляет сообщения и сбрасывает состояние сессии, сохраняя заявки.
`delete_leads` удаляет заявки сессии и их задачи/журналы уведомлений.
`delete_session` каскадно удаляет сессию, историю, заявки и уведомления.
Все операции требуют секрет владельца сессии. Эти функции ещё не подключены к UI.
Удаление строк БД не удаляет автоматически данные из резервных копий и уже
доставленные внешние сообщения; сроки хранения и процессы удаления нужно согласовать
до публичного запуска.

## Проверки без облака

Результат проверки этого этапа на Python 3.10.1: **53 Python-теста прошли**
(14 новых тестов БД и 39 предыдущих). На временном PostgreSQL 17.6 успешно
выполнены сама схема и SQL-проверки: права/RLS, изоляция сессий, порядок и повторы
сообщений, конфликт версии состояния, отказ без согласия, идемпотентность заявки,
откат при ошибке outbox, шесть одновременных повторов и каскадное удаление.
Временный сервер остановлен, тестовый кластер удалён.
`--check-db` без настроек корректно завершился до обращения к сети.
Эти результаты не подтверждают облачное подключение Supabase.

```powershell
.\.venv\Scripts\python.exe -m pytest -q
# Дополнительно, если PostgreSQL установлен и его утилиты доступны в PATH:
.\.venv\Scripts\python.exe .\tests\check_schema_local.py
```

Локальная SQL-проверка создаёт отдельный временный кластер, запускает его на случайном
порту 127.0.0.1 с паролем, проверяет SQL и права, затем останавливает и удаляет
тестовый кластер. Существующие базы PostgreSQL не используются.
При ограничениях Windows запуск сервера может требовать разрешения вне песочницы.
Проверка локального PostgreSQL не подтверждает работу облачного Data API Supabase.

До оценки фактической инфраструктуры, локализации и трансграничной передачи
не используйте реальные данные клиентов. Настройка этой схемы сама по себе
не означает готовность к публичной обработке персональных данных.
